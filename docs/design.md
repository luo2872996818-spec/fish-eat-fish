# 设计文档 · 大鱼吃小鱼

> 这份文档回答「怎么做」：用什么技术、分几个模块、数据怎么流动、为什么这么选。
> 设计变了就回来更新它。

---

## 1. 技术选型

| 项目 | 选择 | 为什么 |
|---|---|---|
| 语言 | 原生 JavaScript（ES Module，`import/export`） | 零依赖、免安装；分文件才有清晰边界，不靠 `<script>` 先后顺序 |
| 渲染 | Canvas 2D | 手机上画几十条鱼稳稳 60 帧；比 DOM 操作快得多 |
| 构建工具 | **不用** | 没有 npm、没有打包步骤 —— 改完代码刷新就能看到效果，这对学习最重要 |
| 字体/图标 | 系统字体 + 内联 SVG | 零额外请求 |
| 托管 | GitHub Pages | 免费、给个链接就能玩 |
| 测试 | Node 内置 `node:test` + `tools/check-deploy.mjs` | 不用装任何框架 |

**没选**：C++/EasyX（手机跑不了）、pygame（手机部署麻烦）、游戏引擎（对这个体量太重）、
React/Vue（这个项目用不上）。

## 2. 架构概览：为什么要分「游戏逻辑」和「平台适配」两层

```
┌─────────────────────────────────────────────────────────┐
│  游戏逻辑层（只管玩法，不知道"屏幕多大""手指还是鼠标"）      │
│                                                          │
│   main/   scenes/   entities/   systems/                 │
│   入口     菜单·游戏·结束   玩家鱼·敌鱼    生成·碰撞·渲染·难度 │
└───────────────────────────┬─────────────────────────────┘
                            │ 只通过这一层暴露的抽象交互
┌───────────────────────────▼─────────────────────────────┐
│  平台适配层 platform/（把"设备差异"全部关在这里）           │
│                                                          │
│   viewport.js  尺寸、DPR、坐标换算                         │
│   input.js     触摸 / 鼠标 / 键盘 → 统一的 input.target     │
│   device.js    设备能力探测（安全区、是否触摸设备）           │
│   storage.js   本机最高分                                   │
└─────────────────────────────────────────────────────────┘
```

**最重要的架构纪律**：

> 游戏逻辑层**绝不**直接写 `addEventListener`，也**绝不**直接读 `event` 对象。

这条纪律换来的是：将来要加键盘操作、改横屏、上微信小程序，
**只改 `platform/` 一个文件夹**，上面那层一行都不用动。

## 3. 模块划分

| 文件 | 职责 | 不负责什么 |
|---|---|---|
| `main/main.js` | 启动：初始化输入、尺寸监听、启动循环 | 不含玩法 |
| `main/game-loop.js` | 固定步长的游戏循环（见第 5 节） | 不知道画面里有什么 |
| `main/config.js` | **所有可调数值**：速度、半径、判定比例、难度曲线 | 没有任何逻辑 |
| `scenes/menu.js` | 主菜单场景 | |
| `scenes/play.js` | 游戏中场景：调度生成/碰撞/渲染 | |
| `scenes/gameover.js` | 结束面板：分数、最高分、重开按钮 | |
| `entities/player.js` | 玩家鱼：位置、速度、朝向、等级、生命、无敌计时 | 不判定碰撞（那是 systems 的事） |
| `entities/enemy-fish.js` | 敌方鱼：位置、速度、半径、种类 | |
| `systems/spawn.js` | 从屏幕外生成敌鱼、出界回收（对象池） | |
| `systems/collision.js` | 圆形碰撞判定 → 吃掉 / 受伤 / 互穿 | 不改分数（只报告结果） |
| `systems/render.js` | 画背景、气泡、鱼、HUD | 不改任何状态 |
| `systems/difficulty.js` | 按等级和时间算"大鱼生成权重" | |
| `platform/*` | 见第 2 节 | 不含玩法 |
| `utils/math.js` | clamp / distance / randomRange / lerp | 通用工具，与游戏无关 |
| `utils/pool.js` | 对象池 | |

> 每个文件只干一件事，函数不超过 50 行 —— 这是 `AGENTS.md` 的编码规范要求。

## 4. 数据流（一帧里发生了什么）

```
手指按下
   ↓
platform/input.js  收到 pointerdown
   ↓  platform/viewport.toWorld() 把屏幕坐标换算成世界坐标
input.target = { x, y }        ← 游戏逻辑层只能看到这一个值
   ↓
systems/player-control   算出"该往哪个方向加速"（朝 target）
   ↓
entities/Player.update(dt)   加速度 → 阻尼 → 限速 → 移动 → 朝向
   ↓
entities/Enemy.update(dt)    匀速直线移动，出界标记回收
   ↓
systems/collision   两两配对做圆碰撞判定
   ↓  返回结果
分数+ / 等级+ / 生命- / 无敌计时开始     （改的是 entities 和 scene 的状态）
   ↓
scenes/*  检查状态：命掉光了没？→ 决定是否切到结束场景
   ↓
systems/render   把当前状态画出来（只读，不改）
```

## 5. 关键设计决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 世界坐标 | **世界大小 = 屏幕可视区**（CSS 像素） | 竖屏、横屏、手机、电脑全都自然成立，不用为每种屏幕设计一套世界；鱼的位置直接用屏幕坐标存，省掉来回换算 |
| 输入事件 | **Pointer Events**（`pointerdown/move/up`） | 浏览器把手指/鼠标/触控笔统一成了 pointer 事件，一套代码三种设备通用，不用写 `if (是手机)` |
| 画布清晰度 | 物理像素 = CSS 像素 × **DPR(封顶 2)** | 设成 3 清晰度提升有限，但每帧要填充的像素翻 2.25 倍，手机会掉帧 |
| 游戏循环 | **固定步长**（累加器 + 固定 1/60 秒步进） | 手机偶尔卡顿时，如果直接用"这帧过了多久"来推进物理，会出现鱼瞬移穿过大鱼的穿透 bug |
| 手指滑出边界 | `setPointerCapture` | 不加的话手指滑出元素范围事件就断了，表现为"鱼卡在半路" |
| 性能 | 对象池 + 实体数量上限 | 手机浏览器里每帧 `new` 对象会产生垃圾回收压力 |
| 数值集中 | 全部放 `config.js` | 调手感时不用翻十个文件 |
| 版本目录 | 游戏放 `v1/`，根目录只放跳转页 | 以后升级 v2 不破坏已分享出去的链接 |
| 尺寸缩放 | 用屏幕短边算"缩放系数 k" | 小屏手机上鱼不能太大，否则没地方躲 |

## 6. 数值表初稿（全部放 `config.js`，玩起来不对就调，不用改逻辑）

> `k` = 缩放系数 = 屏幕短边 / 390（以常见手机的 390 CSS 像素宽为基准）

| 数值 | 初值 | 说明 |
|---|---|---|
| 玩家初始半径 | `18 * k` px | |
| 5 级半径倍数 | `1 / 1.35 / 1.8 / 2.4 / 3.2` | 每级明显变大，肉眼一看就知道升级了 |
| 玩家最大速度 | `260 * k` px/秒 | |
| 玩家加速度 | `900 * k` px/秒² | 决定"跟手"的灵敏度 |
| 阻尼系数 | `3.5` /秒 | 松手后滑行多久停下 |
| 判定：算小鱼 | 敌半径 ≤ 我半径 × **0.85** | |
| 判定：算大鱼 | 敌半径 ≥ 我半径 × **1.15** | 中间区间互不影响，直接穿过 |
| 吃掉的距离条件 | 圆心距 < 我半径 × 0.95 | 嘴碰到才算 |
| 受伤的距离条件 | 圆心距 < 敌半径 × 0.8 | |
| 生命 | 3 条 | |
| 无敌时间 | 1.5 秒 | |
| 同屏敌鱼上限 | `clamp(屏幕面积 / 22000, 12, 34)` 条 | 小屏少、大屏多，保证密度一致 |
| 敌方鱼速度 | 小鱼 80~140，大鱼 40~80 px/秒 | 小鱼灵活难抓、大鱼笨重好躲 —— 这是"手感"的关键 |
| 升到 2/3/4/5 级需累计吃 | `6 / 15 / 28 / 46` 条 | |
| 吃鱼得分 | `round(10 × (敌半径 / 我初始半径) ^ 1.5)` | 越大的鱼分数越高，鼓励冒险 |
| 难度档位 | 每 15 秒提升一档 | 大鱼生成权重 10% → 30% |

## 7. 开发阶段

| 阶段 | 目标 | 验收方式 | 状态 |
|---|---|---|---|
| 0 | 部署自检页 | 手机点开链接有画面、触摸坐标准确、55+ FPS | ✅ 已完成 |
| 1 | 骨架能动 | 一条玩家鱼跟手指游动（有加速度和阻尼）、边界限制正确 | ⬜ |
| 2 | 核心玩法 | 吃小鱼变大、撞大鱼掉命、敌鱼生成回收 | ⬜ |
| 3 | 完整一局 | 三个场景 + HUD + 结束面板 + 重开 + 难度曲线 | ⬜ |
| 4 | 打磨交付 | 真机多分辨率测试、性能优化、文档补齐、项目总结 | ⬜ |
| 5 | 部署上线 | 手机上打开正式链接能玩 | ⬜ |

> 每个阶段都能单独跑起来看到效果。前一阶段没完成，不进入下一阶段。

## 8. 测试方案

| 测什么 | 怎么测 |
|---|---|
| 纯函数逻辑（碰撞判定的三档、等级换算、难度权重） | `tests/*.test.js`，用 Node 内置 `node:test` 跑，不用装框架 |
| 线上是否健康（跳转、404、JS 报错、触摸坐标、帧率） | `node tools/check-deploy.mjs <网址>`，13 项自动检查 |
| 玩法手感 | **只能在真机上玩** —— 模拟器替代不了。帧率、跟手程度都要真机确认 |
| 边界情况 | 手指滑到屏幕外、切到后台再回来、转屏、连撞三次、同一区域鱼特别密 |
